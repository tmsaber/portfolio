NLP Personal Project FORSA tic Hackathon Brief Done

Customer Complaint Classification Algérie Télécom

Built from the Hackathon FORSA tic challenge brief: dialectal NLP and ticket classification for telecom customer support.

View on GitHub Code coming soon Target: Macro F1-Score Language: Algerian Darija & code-switching
Operational context & purpose

Large-scale telecom support, too much to read by hand

Algérie Télécom receives thousands of customer messages every day through social media and its call center. The volume and the mix of dialects and languages make manual triage impossible. This project builds an automated machine learning and NLP approach to classify these complaints by nature, so support teams can route and prioritize them faster.

Challenge breakdown
Unstructured NLP · 9 classes

Challenge 1 — Social Media Comments

Dataset scope: about 30,000 comments from social media (Facebook, Twitter…).

Language: informal text, phonetic spelling, emojis and noisy dialectal slang.

Structured multi-attribute · 6 classes

Challenge 2 — Call-Center Tickets

Dataset scope: complaint tickets recorded by the call-center management system.

Key attributes: service type, technology (ADSL / FTTH / 4G), processing department, location (Wilaya / ACTEL), technical vs commercial type.

Engineering approach
STEP 01

Data Cleaning & Preprocessing

Clean and normalize the text: Darija, Arabic script, French-Arabic mixes, noise and punctuation.

STEP 02

Feature Engineering

Turn text and structured ticket fields into inputs the models can learn from.

STEP 03

Model Training & Validation

Train and compare classification models for each of the two challenges.

STEP 04

Inference & Evaluation

Predict the class of new complaints and evaluate with the Macro F1-Score.

Challenges & objectives

Algerian dialect (Darija)

Non-standard spelling, written in Arabic script and in Latin letters (Arabizi).

Arabic-French code-switching

Customers mix Arabic and French in the same sentence, including technical terms.

Noisy social text

Short, informal comments with emojis, slang and irregular punctuation.

Prioritizing critical cases

The challenge aims to help teams surface urgent complaints first.

Data Personal Project In progress

Dynamic Energy & Cloud Cost Optimizer

SARIMAX-based forecasting to optimize AWS Spot vs On-Demand allocation.

View on GitHub Code coming soon Method: SARIMAX time-series Scope: AWS Auto Scaling Group (cluster level)
Operational context & purpose

Cutting cloud compute cost with forecasting

Cloud compute cost depends on how well capacity is matched to demand. This project forecasts cluster-wide compute load and uses it to decide, hour by hour, how much capacity to run on cheaper but interruptible Spot instances versus reliable On-Demand instances, in order to minimize total cost.

Key design decisions

Cluster-level view

Metrics are aggregated across a whole AWS Auto Scaling Group instead of a single EC2 instance.

Exogenous features

The forecasting model uses Spot price trends, active user load, hour of day and day of week.

24-hour provisioning plan

A decision engine turns the forecast into an hourly Spot / On-Demand schedule.

Engineering architecture
STEP 01In progress

Data Ingestion

Collect CloudWatch Auto Scaling Group metrics and EC2 Spot price history with boto3.

STEP 02Planned

Preprocessing

Clean and resample into an hourly pandas DataFrame, build calendar and exogenous features.

STEP 03Planned

SARIMAX Forecasting

Train a SARIMAX model with exogenous variables to forecast cluster load.

STEP 04Planned

Decision Engine & Dashboard

Generate the 24-hour provisioning schedule and display it in a Streamlit dashboard.

Tools & frameworks
PythonSARIMAXpandasboto3AWS CloudWatchEC2 SpotStreamlit
Where it could go

Designed with a production mindset: the approach could evolve into a FinOps tool for cloud cost optimization.

Vision Team Project · 6 members Done

Fruit Quality Detection FreshClass

Image classification system that grades fruit as Good or Bad using transfer learning (MobileNetV2).

View Team Repository on GitHub Model: MobileNetV2 12 classes (6 fruits × Good/Bad) ~14,800 images
Operational context & purpose

Sorting fruit by quality is slow, subjective and inconsistent between operators. FreshClass automates the grading from a single photo: the user uploads an image and gets a Good (1st choice) or Bad (2nd choice) result with a confidence score.

My role

Documentation Lead & Test Evaluation in a team of 6: README, technical report, code documentation, final presentation, and model testing and evaluation.

Université Badji Mokhtar-Annaba · 8 weeks (Nov–Dec 2025) · Agile sprints with Jira and GitHub

Dataset
Kaggle Fruits 360
Roboflow Universe
Local smartphone photos
AppleBananaGuavaLimeOrangePomegranate

About 14,800 images, balanced to roughly 1,200 per class, each fruit labelled Good or Bad.

Engineering architecture
STEP 01

Data Collection & Cleaning

Merge three sources, remove corrupted images, standardize labels, merge the ambiguous 'Mixed' class into Bad.

STEP 02

Preprocessing

Resize to 128×128, normalize pixels to 0–1, one-hot encode labels, 70/15/15 train/validation/test split.

STEP 03

Model Training

MobileNetV2 pre-trained on ImageNet with a custom dense classifier, trained with Adam and early stopping.

STEP 04

Evaluation

Per-class precision, recall and F1, plus a confusion matrix on the test set.

STEP 05

Deployment

FastAPI REST service in Docker and a Next.js web interface to upload an image and see the result.

Model selection

Five architectures were compared: a custom CNN, VGG16, ResNet50, MobileNetV2 and EfficientNet-B0. MobileNetV2 was selected for its balance of accuracy, small size (about 3.5M parameters) and fast inference.

Challenges solved

Rebalanced the dataset so each class has about 1,200 images.

Ambiguous 'Mixed' class

Merged into Bad after manual review, to match the 1st choice / 2nd choice need.

Corrupted images
